# Analyzer reference prompt

Detailed instructions for Phase 4 (analysis). **Analyze completed benchmark runs** and write a report. The execution phase already produced `artifacts/runs/<run_id>/`; read those artifacts and compare to baseline.

Append `analyzer.started` / `analyzer.finished` to `meta-events.jsonl` per `docs/meta/artifacts-schema.md`.

## Inputs

- `hypothesis_id`, `correlation_id`
- `candidate_run_id` (required), optional `baseline_run_id`
- Paths under `artifacts/runs/<run_id>/`
- Which **validation gate** was completed (`one-task`, `three-task`, or other) — compare baseline and candidate at **that same gate only**

## Outputs

1. Markdown report: `artifacts/meta/analyses/<hypothesis_id>-<candidate_run_id>.md`

---

## Run artifacts (from bench)

Each run writes `artifacts/runs/<run_id>/`:

- MLflow trace: primary observability surface. Start here for span hierarchy, LLM iterations, tool inputs/outputs, evaluation spans, and mirrored trace events.
- `trace.jsonl`: local unified timeline export for grep/scripts and durable path references.
- `result.json`: compact outcome, wall time, patch size, SWE-bench report.
- `patch.diff`: patch generated by the evolving agent.
- `prediction.jsonl`: SWE-bench prediction file.
- `evaluation_stdout.log`, `evaluation_stderr.log`: SWE-bench harness output.
- `agent_events.jsonl`, `llm_calls.jsonl`, `shell_events.jsonl`: secondary JSONL slices.

MLflow spans include benchmark rollout, coding agent session, LLM iterations, workspace tools, evaluation, and trace events mirrored from `trace.jsonl`. The mirrored event names are:

- `run_start`, `task_loaded`, `workspace_prepare_start/finish`, `agent_start`
- `llm_call`: messages, raw response, latency, token usage.
- `invalid_action`: unparseable model output.
- `agent_action`: parsed action and arguments.
- `tool_call`, `shell_command` / `tool_result`, `agent_observation`
- `patch_created`: generated patch and byte size.
- `evaluation_start`, `evaluation_finish`: SWE-bench harness execution and report.
- `run_finish`: final result object.

Do not add SWE-bench gold patch or hidden evaluator fields to agent input or trace.

## How to analyze a trace

1. Open `result.json`. Record `resolved_instances`, `empty_patch_instances`, `error_instances`, `patch_bytes`, `wall_seconds`.
2. Open MLflow (`uv run evolve2 mlflow-ui`, default http://localhost:5050) and inspect the run's span tree. Record LLM calls, tool calls, invalid actions, token usage, and the first span where progress diverged.
3. Use `scripts/summarize_trace.py <run_id>` and `trace.jsonl` only to compute counts, grep event sequences, or cite durable local evidence.
4. Compare each LLM span output with the next `agent_action`/`invalid_action` mirrored event.
5. For each tool span, inspect inputs, outputs, and the next LLM input. Check whether useful evidence was lost, truncated, or ignored.
6. Inspect `patch_created`. If empty, classify why the agent never edited tracked files.
7. Inspect `evaluation_finish.report`. If failed, check `evaluation_stdout.log` / `evaluation_stderr.log`.
8. Write one failure class and one candidate hypothesis.

Common failure classes: `no_patch`, `invalid_action_protocol`, `repeated_action`, `bad_localization`, `bad_patch`, `local_test_failure`, `evaluation_error`, `resolved`.

## Pareto optimization (for reports and recommendations)

### Comparison priorities (lexicographic order)

Compare baseline and candidate at the same gate. For **trace-targeted** hypotheses, also apply §Trace-targeted below.

1. **`patch_published`** (gating): must not regress. A candidate that drops patch publication is disqualified regardless of other diagnostics.
2. **`resolved`**: prefer more tasks solved at equal `patch_published`. A tie on a single task is not a regression signal.
3. **Trace-visible health**: lower `invalid_action_count`, fewer `repeated_action` patterns, clearer `failure_class` progression (e.g. `no_patch` → `bad_patch`), fewer harness errors.
4. **Cost** (`wall_seconds`, tokens, `llm_calls`, `tool_calls`): better at equal outcomes above. Never overrides a clear win on items 1-3.

Break ties using items 2-4 in order. If item 1 differs, the patch-publishing run wins unless the patch is clearly invalid.

**Metric definitions:**

- Gating: `patch_published` — non-empty tracked source diff submitted to SWE-bench evaluation.
- Primary: `resolved` — tasks solved.
- Secondary: `wall_seconds`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `llm_calls`, `tool_calls`, `patch_bytes`, `invalid_action_count`, `failure_class` progression.

A candidate is Pareto-dominant when it has equal or better items 1-2 and improves at least one secondary metric without materially worsening the rest.

### Trace-targeted hypotheses and rejection

A hypothesis is **trace-targeted** when the dossier **Proposed Change** names specific trace-visible outcomes (e.g. lower `invalid_action_count`, fewer `repeated_action`, shorter broken loops).

- Treat **measured improvement** on named trace metrics as **primary positive evidence**.
- **Do not** reject **only** because `resolved` did not increase, if `patch_published` held and named trace metrics improved without material regression on other trace-health signals.
- **Do** reject or `keep unmerged` when there is a **concrete regression**: worse `patch_published`, worse targeted trace metrics, materially worse cost without compensating trace gain, or new failure modes.

If the hypothesis is **not** trace-targeted: diagnostic-only progress needs to connect to `patch_published`, `resolved`, or a confirmed infrastructure fix to justify merge.

Unnamed diagnostic improvements belong in the dossier as follow-up motivation, not merge evidence.

Wall time and token counts are noisy. Do not declare efficiency improvements from one run alone — use at least two comparable runs per side. Time/token metrics are meaningful merge evidence only when both runs reach comparable terminal states. If a run stops before publishing a patch or hits the iteration cap, time/tokens are diagnostic only.

When tradeoffs are unclear, recommend `keep unmerged` or `expand task set` and state which gate to run next — do **not** schedule runs yourself.

State explicitly which gate the executor completed. Do not compare a one-task candidate to a three-task baseline.

## Report template (sections)

1. Run ids and paths
2. Executive summary (one paragraph)
3. Metrics table (baseline vs candidate)
4. Failure class
5. Trace highlights (pointers to line ranges or event types, not full dumps)
6. Pareto assessment
7. **Recommendation** (merge / keep unmerged / reject / rerun / expand task set) — input for Phase 5 merge decision.

Do not print or store secrets from `.env`.
